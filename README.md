# The Judo Waza Book

A community-maintained reference of judo techniques as structured, freely
reusable data: every waza with its canonical Japanese name, what it is, the
key points an examiner looks for, and links to good demonstrations - plus
grading schemes, because belt progressions differ by country and federation.

This repository is the content. [Waza Book](https://wazabook.com), the judo
technique library, is its presentation layer; anything else that can read
JSON can present it too.

## How it is organised

| Path | What it holds |
| --- | --- |
| `techniques/<slug>.json` | One technique per file, every file carrying the same twenty-three fields in the same order. The filename is the canonical id: the lowercase, hyphenated romaji name (`uchi-mata.json`) |
| `grading-schemes/<scheme>.json` | One grading scheme per file: a federation's belt progression, which techniques each grade requires, and (where the official document has been transcribed) each grade's syllabus as printed (`bja-mon.json`). A grade may carry a `beltStripe` where the scheme marks progress with a stripe along one belt, as the Kai grades do |
| `media/grading-schemes/<scheme>/…` | Pictorial syllabus sheets (one per grade) and summary posters, matched to the scheme file by name |
| `skills/<slug>.json` | The examined things that are not techniques: breakfalls (ukemi), gripping (kumi-kata), escapes from a hold, and turnovers |
| `sequences/<slug>.json` | Relationships between techniques: combinations (throw into throw), counters, transitions (throw into groundwork) and groundwork chains; display names derive from the technique names. Each carries the reaction of uke that opens the second technique (`trigger`), whether it throws the same way or the opposite way (`direction`), and the catalogue or document it was read from (`source`) |
| `grips/<slug>.json` | One grip-set per file: which hand goes where (the pulling hand and the lifting hand, by target), which stance game it belongs to, the throws it feeds and in which direction, and what the rules make of it, cited to the rulebook. The `kumi-kata` skills describe the plans that reach a set and the breaks that remove one, and name the sets they work with |
| `guides/<slug>.json` | Everything that is not a technique: essentials (tying a belt), refereeing (commands and signals), and the rules of competition |
| `exams/<slug>.json` | Real grading examinations transcribed as sat: sections, set groupings, items exactly as printed (with resolved technique slugs alongside), pass marks per grade. An examination the federation has replaced is marked `legacy` with a note saying what replaced it, not deleted: it is what older certificates were awarded against |
| `media/techniques/<slug>.webp` | One illustration per technique, matched to `techniques/<slug>.json` by filename; the technique's `image` field carries the alt text and any credit |
| `schema/*.schema.json` | The JSON Schema every file must satisfy; CI enforces it on every pull request |
| `video-providers/<slug>.json` | Whose demonstrations are linked: name, homepage and the default position in the list readers can reorder for themselves |
| `glossary/<slug>.json` | One word a judoka hears on the mat, in plain English, or one of the pieces technique names are built from. Syllabus items resolve to these: "What does matte mean?" is a printed requirement at almost every grade |
| `video-channels/<slug>.json` | Channels worth following, with where each is based. Not providers: nothing on them is indexed technique by technique, so they are never ranked |
| `organisations/<slug>.json` | Governing bodies, their affiliates, and clubs: name, country, the schemes and examinations each owns, and the `parent` chain (club, affiliate, national body) that a reader's country and offered gradings derive from |
| `perspectives/<org>/techniques/<slug>.json`, `perspectives/<org>/exams/<slug>.json` | One organisation's voice on one technique (what its examiners look for, how it teaches it, its local safety rules) or on an examination it owns (how to prepare, which the verbatim transcription deliberately has no field for) - layered over the record only for readers who opt into that organisation's view. Adds context, never overrides: a disagreement with the canonical content is a pull request against that file, for everyone |
| `competition-stats/ijf-technique-frequency.json` | How often each technique scores in IJF competition, by sex, weight class, tier, age group, year, minute of the contest (first minute versus last versus golden score), side (left versus right, whose exact meaning the IJF does not document - see the field's note in the schema before presenting it as anything more) and score type - scoring frequency, because the IJF API only reliably records scores, not attempts. Alongside the techniques, how contests END on penalties: matches decided by a third shido or a direct hansoku-make, and when. Generated by the importer, never edited by hand |
| `competition-stats/ijf-contest-shape.json` | The same crawl read for the contest rather than the score, in eight tables: what wins by how deep in the draw the contest was, which techniques the scorer went on to WIN with as opposed to merely scoring, how contests in a category end and how long they take, every penalty by what it was for and when, what each country scores with, whether scoring first wins, whether scoring with a technique invites an immediate reply, and what gets thrown in the closing minute by whether the thrower was behind. Plus a few real contest clips per technique. Generated by the same run as the frequency file, never edited by hand |
| `competition-stats/ijf-technique-map.json`, `competition-stats/ijf-competition-tiers.json` | The hand-maintained configuration behind it: IJF tag names resolved to technique slugs, and competition names resolved to tiers. An IJF name the map does not carry fails the aggregation loudly so the map gets extended, never silently dropped |
| `tools/ijf-results/` | The importer and aggregator that build `competition-stats/`, with their tests. `npm run ijf:update` runs the whole routine locally: fetch, rebuild, validate, report. The raw crawl cache is local and gitignored; the site builds from the committed files alone, so a failed crawl can never break it |
| `backlog/` | Known gaps, not a submission queue: links from the owner's source spreadsheet that did not attach to anything, kept as evidence of what the reference still lacks. Nothing here is published. Contributions go through a pull request, not through this folder |
| `scripts/validate.mjs` | The same validation, runnable locally: `npm ci && npm run validate` |
| `NOTICE.md` | Rights and provenance: what is licensed, where images came from, and how to have material removed |

Two conventions the table above assumes. `media/` mirrors the content folders:
an illustration for a collection lives in `media/<collection>/`, matched to its
entry by filename, and the site publishes it at `/images/<collection>/`. Adding
a media folder that is not named after a collection puts it at a URL nothing
links to. And `scripts/` and `tools/` divide by when they run, not by what they
are: `scripts/` is what CI runs on every pull request, so it must stay fast and
must never write to the repository; `tools/` is run on demand and does write,
which is why the importer lives there and the validator does not.

Three design rules shape everything:

- **Technique identity is universal.** The romaji slug and the kanji are the
  same for everyone and are never translated. Alternative romanisations go in
  `aliases`.
- **Prose is localised, grading is local.** Reader-facing text is an object
  keyed by BCP 47 language code with `"en"` required (`"gloss": { "en":
  "inner thigh throw", "fr": "…" }`). Grading schemes are separate files
  precisely so that no country's progression is treated as the default.
- **A technique record is canonical, and gaps are written down.** Every
  technique file carries every field, in one order, whether or not anyone has
  filled it in: a field nobody has written yet is `null`, or `[]` where it is
  a list, never absent. So a page can tell a reader what it is missing rather
  than quietly omitting it, and `npm run validate` ends by counting the gaps -
  including the throws that have no counter recorded against them, which live
  in `sequences/` and are the easiest useful thing to contribute. A sequence
  is canonical the same way, and carries the same three narrated fields as a
  technique: the step-by-step, the receiving note and the notes for visually
  impaired judoka, written for the pair rather than for either technique.

Prohibition comes in two degrees, and `banned` says which. `"in-competition"`
is a technique contest rules bar but judo still teaches, demonstrates and
examines, such as the leg grabs and standing waki-gatame: it is written up in
full. `"yes"` is a technique not to be applied at all, documented for
recognition and refereeing with a `bannedNote` saying why and deliberately no
step-by-step instruction. Everything else is `"no"`.

`banned` answers whether judo applies the technique at all. What a referee does
about it is a different question with a different answer, and `contest` carries
that one: `"penalised"` where applying it draws a shido, `"prohibited"` where it
draws a direct hansoku-make, `"conditional"` where the penalty depends on the
form, the position or the age group. It is `null` on the great majority of
techniques, which no rule singles out. Every `contest` cites the rulebook it
came from by the `sourceId` of a record in `reference/` and the article numbers
the note paraphrases, because a rule written down without its edition goes wrong
quietly: the leg grabs were written up here as hansoku-make offences when the
IJF had already made them shido.

Where the Kodokan recognises a technique, the file carries its place in that
classification: `kodokanNumber` (101 to 810) and the three-letter
`kodokanAbbr`. Both are null for the variants judo uses that the hundred does
not name, and the validator checks the number agrees with the `category` and
`wazaType` already recorded.

A third rule follows from a project tenet: **this reference must be valuable
to visually impaired judoka**. We cannot caption or audio-describe other
people's videos, so the written content is the accessibility layer. Each
technique's `described` field narrates the whole movement for the ear, step
by step, and video entries record whether the footage carries captions and
spoken instruction. When writing, assume the reader may never see the video.

## Running it locally

You need [Node.js](https://nodejs.org) 22 or newer. After cloning, install the
dependencies once - there is one, the JSON Schema validator `ajv`:

```sh
npm ci
```

Then:

```sh
npm run validate                   # the three passes CI runs on every pull request
npm run video -- "<video url>"     # turn a pasted link into the video entry to paste in
```

`npm run validate` ends by counting what the reference is still missing, which
is the quickest way to find something worth contributing. Nothing else here
needs building: the content is plain JSON and every file can be read and
edited on its own.

## Contributing

Yes please. The most valuable pull requests are also the smallest: a better
demonstration video, a translation, a correction to a key point, your
federation's grading scheme. See [CONTRIBUTING.md](CONTRIBUTING.md) - it
includes a copy-paste template for each kind of change, and CI validates
every file mechanically so review can focus on the judo.

This is a community reference and it improves by pull request. Forking is
your right under the licence - but a fix that lands here reaches everyone,
including every fork, so please send it here first. And if you are forking
because something here blocks you, open an issue before you do: we would
rather change it than have the reference split in two.
